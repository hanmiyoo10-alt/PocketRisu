## Meaningful transferable idea

### PERSISTENT-VOLUME-CREDENTIAL-RECOVERY-BOUNDARY

A failed first install can create persistent database/object-store volumes before application readiness succeeds. If rollback then restores or removes the generated credential/config state while those volumes retain the generated credentials, the next lifecycle command can strand otherwise intact persistent data behind unknown credentials.

Haejeok's fix treats persistent-volume creation as an irreversible-enough ownership boundary for credential handling: once persistent volumes exist, failed install recovery keeps the protected generated configuration, reports the likely authentication failure, and gives explicit recovery commands instead of blindly restoring the pre-install credential state. Its regression test simulates volume creation plus readiness authentication failure, verifies PostgreSQL/RustFS credentials remain persisted, verifies transaction debris is absent, and confirms a subsequent rebuild can proceed.

Release-tag verification/download-pin changes are useful deployment hygiene but are source-specific release plumbing and were not promoted to a separate PocketRisu idea in this pass.
