## Meaningful findings

### SHARED-CACHE-DETACHED-METADATA-OWNERSHIP

Source: `9ff600a2c754d9aa203da65e9e3b84c2ceadf3e7`

HypaProcessorV2 previously mutated the `memoryVector` object returned by the shared persisted/in-memory embedding cache by assigning call-specific metadata directly to it. A later cache hit for the same embedding key with `metadata === undefined` could therefore erase metadata owned by an already-indexed summary and crash similarity-result handling. The fix creates a detached result envelope (`{ ...cached, id, metadata }`) before attaching request-local metadata and before storing it in the processor-local vector map.

Invariant: shared cache objects are reusable value records, not writable request-local envelopes. Call-specific metadata/identity must be attached to a detached object. A metadata-less lookup must never mutate or clear metadata attached to another consumer's processor-local result.

The same commit also bounds embedding error bodies before surfacing them in chat UI. That is useful defensive UI behavior but is not promoted as a separate idea in this slice.

### LIVE-SEND-RECOVERY-OWNERSHIP-GATE

Source: `2c6cc72413e9a48a28bb625d39d38975b105993d`

Terminal job recovery could race a still-live send after tab thaw/reattach: both paths could try to fill the same message, save, claim the job, and emit request-log state. The fix checks generation ownership before recovery slot-in. Only a `live` generation owner blocks recovery; a `background` registration does not. If the live path later dies, releasing its generation guard allows the next recovery pass to proceed.

Invariant: terminal recovery is a fallback owner and must not mutate/claim a chat while the live send path still owns that chat. The gate must be ownership-kind-specific rather than a blanket "any generation state" block.

### PER-CHAT-MEMORY-PRESET-BINDING — adopted slice / evidence merge

Source: `0ab8207ccbe52a251d146e0e24e1868f0cad1a18` plus follow-up localization/version commits through reviewed HEAD.

This is the official PocketRisu realization of the existing Risu-family idea to scope long-term-memory behavior to the source chat. `memoryPresets` becomes the canonical configuration, while each chat can bind to a specific preset, explicit `off`, or `default` inheritance. The implementation deliberately keeps legacy Hypa fields as a compatibility mirror rather than an alternate authority, and migration avoids silently enabling memory for legacy chats that never opted in.

Deduplication decision: do not create a second broad "per-chat memory" idea. Merge this evidence into the existing memory-scope idea and treat the *per-chat preset binding slice* as ADOPTED. Broader saved-chat/memory-workspace semantics not covered by this commit remain outside that adopted slice.
