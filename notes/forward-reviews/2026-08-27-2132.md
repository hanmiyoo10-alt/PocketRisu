Source: `nevaeh5379/HaejeokRisuai` `67cd018beb90647c9022ef76744fd86bad7af348` (merged by `1d39547e04f529deb7da2ca7d661d371a81cbd20`).

- Dependencies: PocketRisu current local-restore format ownership, Android/Capacitor restore path, raw legacy backup compatibility and rollback audit
- Priority: `P2`
- Lifecycle status: `DESIGN_NEEDED`

Source evidence: the old path attempted container parsing and, on any container error, retried the whole input as a raw database. A truncated/full-disk/malformed multi-GB container could therefore change format after partial parsing and be copied into WebView-facing restore, creating an OOM/corruption hazard. The fix performs format admission before extraction, refuses oversized raw DB input, validates entry length against remaining bytes, stages/cleans on failure, and streams Android SQLite restore statements inside the native transaction instead of retaining the entire flattened statement/value list.

Expected PocketRisu benefit: explicit format ownership prevents error-class confusion; bounded restore materialization lowers peak WebView/native memory; malformed/truncated backups fail closed instead of silently switching restore mode.

Main risk/conflict: restore is destructive/high-blast-radius and current PocketRisu architecture may not share Haejeok's Capacitor path or limits. A hard-coded 512 MiB threshold is source-specific evidence, not authority. Do not copy the value or native mechanism blindly.

Validation need: identify all accepted backup formats; test raw/container ambiguity, truncated headers/entries, disk-full staging, cleanup after failure, legacy raw restore, multi-thousand-entity restore, transaction rollback, peak RSS/WebView heap, and no publish of partially restored state.

Follow-up: assistant-owned design dossier created in helper repo; remain design-only until current PocketRisu restore ownership is mapped.
