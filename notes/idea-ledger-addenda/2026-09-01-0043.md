## SHARED-CACHE-VALUE-MUTATION-BOUNDARY

- System impact: `NO_SYSTEM_UPDATE`
- Importance: `HIGH`

- Source evidence: `PocketRisu/PocketRisu@9ff600a2c754d9aa203da65e9e3b84c2ceadf3e7`. `HypaProcessorV2` previously mutated `metadata` directly on a shared object returned from the in-memory vector cache. A metadata-less query hitting the same key could then clear metadata retained by an earlier consumer and cause similarity-search failure. The adopted fix derives a caller-owned result object before attaching `id` and `metadata`.
- Benefit: prevents cross-consumer state contamination and Hypa crashes without giving up shared embedding-cache reuse.
- Conflict/risk: copying should stay narrow; blindly deep-cloning large vector payloads would trade correctness for unnecessary allocation pressure.
- Validation need: use two consumers of one cache key with differing metadata requirements; confirm cache hits remain shared for immutable vector data while caller metadata cannot mutate another consumer's result.
- Follow-up: preserve this invariant for Hypa/vector cache refactors and inspect other shared-reference caches opportunistically rather than assuming all caches need cloning.

Deduplication note: this is distinct from request-cache scoping/coalescing ideas. Those govern key/scope/lifetime; this invariant governs mutation ownership of a value already returned from a shared cache.
