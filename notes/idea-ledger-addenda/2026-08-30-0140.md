- Conflict/risk: blindly introducing a broad flush can increase backup latency, entangle independent save chains, or regress PocketRisu's existing save/integrity optimizations. The participant set must be complete and owned explicitly; this must not become a visibility/pagehide flush path.
- Validation need: identify each PocketRisu owner that can buffer state ahead of durable storage; reproduce export while at least one owner is dirty; prove the resulting snapshot contains the latest state only after the barrier; verify failure is fail-closed if a participant cannot flush; verify `flushServerDbKeepalive()` and existing save behavior remain unchanged.
- Follow-up: assistant-owned design dossier at `products/pocketrisu-helper-mod/docs/features/backup/backup-snapshot-durable-store-barrier/DESIGN.md`; first engineering slice is test-only ownership/reproduction. Do not implement until the PocketRisu gap is demonstrated.

Deduplication note: this is narrower than the existing staged-import publish barrier and crash-safe write ideas. Those govern candidate publication / write atomicity; this item governs the pre-export consistency boundary across independently buffered state owners.
