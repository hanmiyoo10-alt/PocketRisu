### Update-safe custom backup directory ownership

- `System impact`: `NO_SYSTEM_UPDATE`
- `Importance`: `HIGH`
- `Difficulty`: `MEDIUM`
- `Size`: `S`
- `Evidence`: `MEDIUM`
- `Risk`: `HIGH`
- `Dependencies`: current PocketRisu self-update/update-replacement ownership audit; determine whether configurable server backup paths can be inside the install tree and how updater keep/delete roots are owned
- `Priority`: `P1`
- lifecycle status: `DESIGN_NEEDED`
- source evidence: `PocketRisu-Alter/PocketRisu-Alter` `922bd30f70989a9a4af01d4d7b017fe6c05b8226`
- benefit: prevent in-place updates from deleting user-owned backups because user-data paths and updater-owned application paths share an install root
- conflict/risk: destructive updater boundary; path canonicalization and stale marker/config state can either delete data or accidentally preserve executable/app files
- validation need: inspect current PocketRisu updater + backup-path ownership first; if applicable, test managed roots, safe user-data roots, outside-root paths, root itself, canonicalization/traversal, stale/missing state, ambiguous ownership fail-closed behavior, and rollback
- follow-up: `products/pocketrisu-helper-mod/docs/features/backup/update-safe-backup-directory/DESIGN.md`; keep design-only until the PocketRisu applicability dependency is resolved and high-risk updater invariants are proven

Deduplication note: this is related to backup/recovery safety but is not the same underlying idea as restore-format admission or backup-content integrity. It concerns ownership during application replacement/update, so it remains a separate design record.
