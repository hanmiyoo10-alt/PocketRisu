- benefit: preserve the exact generated credentials/config that already own newly-created persistent volumes when readiness fails, so a failed install does not strand persistent data behind credentials that rollback discarded.
- conflict/risk: deployment and credential ownership are security-sensitive. The wrong preservation boundary can retain secrets unnecessarily or bind future lifecycle commands to stale/untrusted volumes. Do not guess credentials, silently rewrite volume auth, or auto-delete volumes.
- validation need: map PocketRisu's install transaction phases; identify the first persistent credential-binding operation; test failures before and after that boundary; verify protected state permissions; distinguish generic readiness failure from authentication failure; prove subsequent rebuild/start recovery and rollback cleanliness.
- follow-up: maintain an assistant-owned design dossier. Remain design/investigation only under current autonomous safety gates (`SYSTEM_UPDATE_REQUIRED`, credential/deployment boundary, `Risk: HIGH`).

Deduplication note: this is not the backup durability-barrier idea. That idea protects snapshot freshness before backup; this one protects persistent deployment identity/credentials after a partially committed install.
