## Android native self-updater trust boundary

- `System impact`: `SYSTEM_UPDATE_REQUIRED`
- `Importance`: `HIGH`
- `Difficulty`: `HIGH`
- `Size`: `M`
- `Evidence`: `MEDIUM`
- `Risk`: `HIGH`
- `Dependencies`: explicit PocketRisu Android/native-client substrate and release-signing/provenance policy; installer-permission UX; rollback/recovery contract
- `Priority`: `P2`
- lifecycle status: `DESIGN_NEEDED`
- source evidence: `nevaeh5379/HaejeokRisuai` `af1d48cc9f8fe6d1f4350558b70f424cbb92830f`
- benefit: a future native PocketRisu client could update without manual APK replacement while bounding download size and validating the downloaded package before installer handoff.
- conflict/risk: `REQUEST_INSTALL_PACKAGES` crosses a device/package-install boundary. A SHA-256 value fetched from the same release origin as the APK protects against corruption but is not, by itself, independent authenticity if that origin is compromised. Incorrect package/version/provenance handling could install an untrusted or unintended build. Current PocketRisu has no matching Capacitor/native Android owner.
- validation need: signed/provenance-verifiable release metadata; package/signing-certificate identity verification; downgrade/replay rejection; bounded manifest/APK sizes; interrupted-download cleanup; installer-permission denial path; update-source failure; post-update compatibility/rollback; no Android notification side effects on the server phone.
- follow-up: keep design/investigation only. Do not implement unless a native Android client becomes an explicit PocketRisu direction and the user gives a narrower implementation instruction consistent with the system-update/security gate.

### Design invariant

Treat updater metadata, payload, package identity, signing identity, version monotonicity, installer authorization, and rollback as separate trust checks. Transport hash equality is necessary for integrity but must not be treated as the sole release-authority proof.
